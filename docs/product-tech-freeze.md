# 产品与技术冻结说明

## 1. 文档目的

本文档用于冻结 MVP 开发前必须统一的产品和技术决策，避免前后端在开发中反复修改基础规则。

本文档对应任务看板中的：

- `PM-001` 确认产品名称与语言策略
- `PM-002` 确认默认币种和金额单位
- `PM-003` 确认打卡规则
- `PM-004` 确认关系规则
- `PM-005` 确认插画资源策略
- `PM-006` 冻结 MVP 接口字段

如后续确需修改本文件中的冻结项，建议以“变更记录”的方式追加，不直接覆盖原决策。

## 2. MVP 产品定位冻结

### 2.1 产品定位

首期产品定位为：

> 面向情侣/亲密关系双方的移动端陪伴 Web App，通过每日心情打卡、共同目标、日历回顾和今日一言，形成轻量但持续的双人互动仪式。

核心关键词：

- 双人关系
- 每日打卡
- 心情日记
- 共同目标
- 日历回顾
- 今日一言
- 轻甜治愈视觉

### 2.2 首期目标用户

首期默认面向中文用户，但保留参考图中的日系轻甜视觉气质。

默认假设：

- 用户主要使用移动端浏览器访问。
- 用户对产品的期待是“轻量、好看、有仪式感”，不是复杂社交平台。
- 一段关系中只有两个人。
- 使用频率以每天 1-2 次为主。

## 3. 产品名称与语言策略

### 3.1 产品名称

MVP 阶段暂用产品名：

```text
TwoDays
```

说明：

- 与参考图保持一致，便于开发和设计延续。
- 后续正式发布前可再做品牌命名。
- 代码中的应用名可使用 `TwoDays`。
- 页面标题、manifest、OpenGraph 信息暂用 `TwoDays`。

### 3.2 默认语言

MVP 默认语言：

```text
zh-CN
```

UI 文案使用简体中文。

参考图中的日文文案不直接作为首期默认文案，但可保留在视觉气质中，例如：

- 柔和粉色
- 卡片式布局
- 可爱插画
- 轻量仪式感

### 3.3 多语言策略

MVP 不做完整多语言系统。

保留字段：

- `users.locale`

后续可支持：

- `zh-CN`
- `ja-JP`
- `en-US`

首期前端可以先把文案集中放在常量文件中，便于后续国际化。

## 4. 默认币种与金额规则

### 4.1 默认币种

MVP 默认币种：

```text
CNY
```

显示格式：

```text
¥70,000
```

说明：

- 面向中文用户时，默认共同目标更适合人民币语境。
- UI 可以使用 `¥`，无需在每个金额后重复展示 `CNY`。
- 后端字段仍保留 `currency`，便于后续支持 `JPY`。

### 4.2 金额存储单位

后端金额统一使用整数存储。

对于 `CNY`：

```text
1 元 = 100 分
```

示例：

| 展示金额 | 后端存储 |
| --- | --- |
| ¥1.00 | 100 |
| ¥70,000.00 | 7000000 |
| ¥100,000.00 | 10000000 |

前端展示时：

- 默认显示整数元。
- 如果金额不能被 100 整除，再显示两位小数。

### 4.3 金额输入规则

MVP 金额规则：

- 目标金额必须大于 0。
- 添加金额必须大于 0。
- 不支持负数流水。
- 不支持撤销流水。
- 不支持多币种目标混合。
- 同一个目标固定一种币种。

## 5. 打卡规则冻结

### 5.1 每日打卡定义

每日打卡包含：

- 心情：必填
- 日记：选填
- 所属日期：后端根据用户时区计算

首期心情枚举：

| 值 | 中文显示 | 说明 |
| --- | --- | --- |
| `happy` | 开心 | 正向状态 |
| `normal` | 普通 | 中性状态 |
| `sad` | 难过 | 低落状态 |

### 5.2 打卡频率

MVP 规则：

- 每个用户每天最多一条有效打卡。
- 当天允许编辑或覆盖更新。
- 不允许提交未来日期。
- 不支持补签历史日期。

后端实现建议：

- 使用 `upsert` 写入今日打卡。
- 唯一约束：`relationship_id + user_id + checkin_date`。

### 5.3 打卡日期与时区

MVP 默认使用用户时区计算业务日期。

默认时区：

```text
Asia/Shanghai
```

说明：

- 用户注册时默认 `Asia/Shanghai`。
- 后端返回 `checkinDate`，前端不自行推导业务日期。
- 日历页以接口返回日期为准。

### 5.4 连续打卡规则

连续打卡定义为：

> 双方都完成打卡的连续自然日数量。

计算规则：

1. 从今天往前检查。
2. 如果今天双方都完成，则今天计入。
3. 如果今天只有一方完成，则展示昨天为止的连续天数，并通过 `todayCompletedByMe` / `todayCompletedByPartner` 表达今日状态。
4. 遇到任意一天不是双方完成，则连续统计停止。

## 6. 关系规则冻结

### 6.1 关系人数

MVP 规则：

- 一个关系最多两名有效成员。
- 一个用户同一时间只能处于一个有效关系。
- 关系创建后默认为 `pending`。
- 第二名用户加入后变为 `active`。
- 解除后变为 `broken`。

关系状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已创建，等待对方加入 |
| `active` | 双方已绑定 |
| `broken` | 已解除 |

### 6.2 邀请码规则

MVP 邀请码规则：

- 邀请码由后端生成。
- 邀请码唯一。
- 长度建议 6 位。
- 使用大写字母和数字。
- 避免容易混淆字符，如 `O`、`0`、`I`、`1`。

示例：

```text
A8X2KQ
```

### 6.3 解除关系规则

MVP 规则：

- 任意一方可以发起解除关系。
- 前端必须二次确认。
- 后端接口必须要求 `confirm: true`。
- 解除关系后，不允许继续写入打卡、目标、消息。
- 历史数据保留。

## 7. 消息规则冻结

### 7.1 消息类型

MVP 消息类型：

| 类型 | 含义 |
| --- | --- |
| `daily_word` | 今日一言 |
| `reply` | 普通回复 |
| `system` | 系统消息 |

### 7.2 内容限制

规则：

- 消息内容必填。
- 消息最大 500 字。
- 删除消息使用软删除。
- 用户只能删除自己发送的消息。
- 查询默认不返回已删除消息。

### 7.3 今日一言

首页的今日一言使用 `messages` 表承载。

规则：

- `messageDate` 默认为今天。
- `type` 可使用 `daily_word`。
- 首期不限制每天只能发送一条今日一言。

## 8. 目标规则冻结

### 8.1 目标数量

MVP 规则：

- 每个关系同一时间只允许一个 `active` 目标。
- 目标达成后状态变为 `completed`。
- 已完成目标不继续添加金额。
- 创建下一个目标作为后续功能入口，可首期保留按钮但不强制完整实现多目标历史切换。

### 8.2 目标金额

规则：

- `targetAmount` 必须大于 0。
- `currentAmount` 初始为 0。
- `currentAmount` 只通过 `goal_entries` 累加。
- 添加金额和更新目标必须在同一事务中完成。

### 8.3 目标达成

达成条件：

```text
currentAmount >= targetAmount
```

达成后：

- `status = completed`
- `completedAt = now`
- 前端展示目标达成页

## 9. 日历规则冻结

### 9.1 月历数据

日历接口以月份为查询单位：

```text
GET /calendar?month=YYYY-MM
```

### 9.2 日期状态

状态枚举：

| 状态 | 含义 |
| --- | --- |
| `both` | 双方都打卡 |
| `me_only` | 只有当前用户打卡 |
| `partner_only` | 只有对方打卡 |
| `none` | 双方都未打卡 |
| `future` | 未来日期 |

前端只负责展示接口返回状态，不自行合并双方记录。

## 10. 技术栈冻结

### 10.1 前端

MVP 默认技术栈：

| 类型 | 选型 |
| --- | --- |
| 框架 | Vite + React |
| 语言 | TypeScript |
| 路由 | React Router |
| 请求缓存 | TanStack Query |
| 表单 | React Hook Form + Zod |
| 样式 | Tailwind CSS |
| 图标 | lucide-react |
| 日期 | dayjs |
| 测试 | Vitest + React Testing Library |
| E2E | Playwright |

### 10.2 后端

MVP 默认技术栈：

| 类型 | 选型 |
| --- | --- |
| 框架 | NestJS |
| 语言 | TypeScript |
| 数据库 | PostgreSQL |
| ORM | Prisma |
| 缓存 | Redis |
| 认证 | JWT + Refresh Token |
| API 文档 | OpenAPI/Swagger |
| 测试 | Jest + Supertest |

### 10.3 仓库结构

MVP 建议使用单仓库：

```text
apps/
  web/
  api/
packages/
  shared/
docs/
```

说明：

- `apps/web` 放前端。
- `apps/api` 放后端。
- `packages/shared` 后续可放共享类型、工具函数。
- 当前阶段先保留 `docs` 文档集。

## 11. 接口字段冻结

MVP 接口以以下文件为准：

```text
docs/openapi.yaml
```

冻结范围：

- 路由路径。
- HTTP 方法。
- 认证方式。
- 请求字段。
- 响应字段。
- 枚举值。
- 统一错误结构。

可以继续补充：

- 字段描述。
- 示例。
- 更细的错误详情。

不建议随意修改：

- 核心字段命名。
- 枚举值。
- 响应包裹结构。
- 金额单位。
- 日期格式。

## 12. 数据库设计冻结

MVP 数据库以以下文件为准：

```text
docs/database-schema.md
```

冻结范围：

- 核心表结构。
- Prisma model 命名。
- enum 命名。
- 关键唯一约束。
- 目标金额事务规则。
- 打卡唯一规则。
- 关系权限规则。

允许实现时微调：

- 字段注释。
- 默认头像策略。
- seed 数据内容。
- migration 文件拆分方式。

## 13. 首期延期项

以下功能明确不进入 MVP 必做范围：

- 多语言完整切换。
- 原生 App。
- 复杂 PWA 离线能力。
- 图片日记。
- 语音消息。
- 视频消息。
- AI 情绪分析。
- 多目标并行。
- 关系历史恢复/切换。
- 完整管理后台。
- Web Push 正式推送。
- PDF 回忆册导出。
- 复杂主题换肤。

## 14. MVP 验收口径

MVP 是否完成，以以下条件为准：

- 两个用户可以通过邮箱验证码登录。
- 用户 A 可以创建关系并复制邀请码。
- 用户 B 可以通过邀请码加入。
- 首页显示双方关系、关系天数、连续打卡和今日状态。
- 双方可以提交今日心情打卡。
- 打卡完成页和等待对方页可用。
- 用户可以创建或查看一个共同目标。
- 用户可以添加目标金额。
- 日历可以显示某月双方打卡状态。
- 用户可以发送和查看消息。
- 我的页面可以展示邀请码和基础设置。
- 主要移动端宽度无明显布局问题。
- 关键接口都有权限校验。
