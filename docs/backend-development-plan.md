# 后端开发计划

## 1. 开发目标

基于 `backend-requirements.md`，后端首期目标是完成情侣陪伴类 Web App 的 MVP 服务端能力。

MVP 必须支持：

- 邮箱验证码登录。
- 用户创建情侣关系与邀请码加入。
- 获取首页聚合数据。
- 每日心情打卡。
- 日历月数据聚合。
- 共同目标和金额流水。
- 今日一言/消息。
- 我的页面设置与邀请码。
- 关系数据权限校验。

首期不强制实现完整后台管理、复杂通知、图片上传、语音消息、AI 分析、PDF 导出。

## 2. 推荐技术选型

默认后端技术栈：

| 类型 | 选型 | 说明 |
| --- | --- | --- |
| 框架 | NestJS | 模块化清晰，适合中小型业务服务 |
| 语言 | TypeScript | 与前端共享类型成本较低 |
| 数据库 | PostgreSQL | 适合关系数据、事务和约束 |
| ORM | Prisma | schema 清晰，迁移方便 |
| 缓存 | Redis | 验证码、限流、短期缓存 |
| 认证 | JWT + Refresh Token | Web App 常用方案 |
| 队列 | BullMQ | 后续通知、数据导出可用 |
| 文档 | OpenAPI/Swagger | 支持前后端并行联调 |
| 测试 | Jest + Supertest | 单元和接口测试 |

如果团队使用 Spring Boot，本计划中的模块、接口和数据规则仍可复用。

## 3. 服务模块划分

建议后端模块：

```text
src/
  app.module.ts
  common/
    decorators/
    filters/
    guards/
    interceptors/
    pipes/
    utils/
  config/
  database/
  modules/
    auth/
    users/
    relationships/
    dashboard/
    checkins/
    goals/
    calendar/
    messages/
    settings/
    exports/
    notifications/
  jobs/
  tests/
```

模块职责：

- `auth`：验证码、登录、刷新 token、退出。
- `users`：用户资料、当前用户。
- `relationships`：创建关系、加入关系、解除关系、成员校验。
- `dashboard`：首页聚合。
- `checkins`：每日心情打卡、时间线。
- `goals`：目标、金额流水、达成判断。
- `calendar`：按月聚合双方打卡状态。
- `messages`：今日一言、回复、删除。
- `settings`：通知、隐私等设置。
- `exports`：数据导出，首期可只保留接口骨架。
- `notifications`：通知能力，首期可只保留服务接口。

## 4. 开发里程碑

### M0：工程初始化与基础设施

目标：搭建后端项目、数据库、配置、日志、错误处理和 API 文档基础。

预计产出：

- 服务可启动。
- 数据库连接可用。
- Prisma schema 初版完成。
- Swagger 可访问。
- 统一响应、异常、鉴权守卫基础完成。

### M1：认证、用户与关系

目标：完成用户进入产品的最小闭环。

预计产出：

- 邮箱验证码发送和校验。
- 用户注册/登录。
- access token 和 refresh token。
- 创建关系、生成邀请码、加入关系。
- 当前关系查询和成员权限校验。

### M2：每日打卡与首页聚合

目标：完成产品最核心业务。

预计产出：

- 用户提交今日心情和日记。
- 查询今日双方状态。
- 计算双方共同连续打卡天数。
- 首页聚合接口返回关系、成员、今日状态、目标摘要。

### M3：目标、日历与消息

目标：完成 MVP 的主要功能模块。

预计产出：

- 创建/编辑目标。
- 添加金额流水并事务更新目标进度。
- 达成目标自动更新状态。
- 日历月聚合。
- 消息发送、查询、删除。

### M4：设置、导出骨架与通知预留

目标：补齐我的页面依赖能力。

预计产出：

- 用户设置读取和更新。
- 数据导出任务接口骨架。
- 通知 token 和通知服务接口预留。
- 解除关系和数据权限处理完善。

### M5：测试、联调与上线准备

目标：让 API 可稳定支撑前端 MVP。

预计产出：

- 核心单元测试。
- 关键接口集成测试。
- Swagger 文档完整。
- 种子数据和本地联调说明。
- 生产环境配置清单。

## 5. 详细任务拆分

### BE-001 项目初始化

内容：

- 初始化 NestJS + TypeScript 项目。
- 配置 ESLint、Prettier、环境变量。
- 配置项目目录结构。
- 配置健康检查接口 `/health`。
- 配置基础启动脚本。

依赖：无。

验收标准：

- 服务可本地启动。
- `/health` 返回正常状态。
- 构建命令可通过。

### BE-002 数据库与 Prisma 初始化

内容：

- 配置 PostgreSQL 连接。
- 初始化 Prisma。
- 建立基础 schema。
- 配置迁移命令。
- 配置 seed 脚本入口。

依赖：BE-001。

验收标准：

- 能执行数据库迁移。
- Prisma Client 可正常生成。
- 本地数据库连接成功。

### BE-003 统一响应与错误处理

内容：

- 实现统一响应结构。
- 实现全局异常过滤器。
- 实现请求 ID。
- 实现参数校验 pipe。
- 定义业务错误码。

依赖：BE-001。

验收标准：

- 成功响应格式统一。
- 错误响应包含 `code`、`message`、`details`、`requestId`。
- 参数错误返回 `VALIDATION_ERROR`。

### BE-004 Swagger/OpenAPI 基础

内容：

- 配置 Swagger。
- 给 DTO 添加接口描述。
- 配置 Bearer Auth。
- 暴露 `/docs` 或 `/api-docs`。

依赖：BE-001、BE-003。

验收标准：

- Swagger 页面可访问。
- 接口请求、响应和错误示例清晰。

### BE-005 用户表与认证基础模型

内容：

- 建立 `users` 表。
- 建立 `auth_codes` 或 Redis 验证码结构。
- 建立 refresh token 存储策略。
- 建立 `user_settings` 表。

依赖：BE-002。

验收标准：

- 数据表迁移成功。
- 邮箱唯一约束生效。
- 用户默认设置可创建。

### BE-006 邮箱验证码发送

内容：

- 实现 `/auth/send-code`。
- 生成 6 位验证码。
- 存储验证码哈希。
- 实现邮箱发送适配器。
- 开发环境可打印验证码或使用 mock mailer。
- 实现发送冷却和 IP 限流。

依赖：BE-003、BE-005。

验收标准：

- 同一邮箱 60 秒内不可重复发送。
- 验证码明文不入库。
- 开发环境可完成登录测试。

### BE-007 验证码登录

内容：

- 实现 `/auth/login`。
- 校验邮箱和验证码。
- 验证成功后创建或获取用户。
- 创建默认设置。
- 返回 access token 和 refresh token。
- 支持可选邀请码加入关系。

依赖：BE-006、BE-010。

验收标准：

- 正确验证码可登录。
- 错误和过期验证码返回明确错误码。
- 验证码使用后不可重复使用。
- 带邀请码登录时可完成关系加入。

### BE-008 Token 刷新与退出

内容：

- 实现 `/auth/refresh`。
- 实现 `/auth/logout`。
- 实现 JWT Auth Guard。
- 实现当前用户 decorator。

依赖：BE-007。

验收标准：

- access token 过期后可通过 refresh token 刷新。
- logout 后 refresh token 失效。
- 受保护接口无 token 返回 401。

### BE-009 当前用户接口

内容：

- 实现 `GET /me`。
- 实现 `PATCH /me`。
- 返回用户资料、设置、当前关系摘要。

依赖：BE-008、BE-010。

验收标准：

- 登录用户可获取自己的资料。
- 可更新昵称、头像、时区、语言。
- 不返回敏感字段。

### BE-010 关系模型与邀请码

内容：

- 建立 `relationships` 表。
- 建立 `relationship_members` 表。
- 实现邀请码生成。
- 实现关系成员数量约束。
- 实现用户当前有效关系约束。

依赖：BE-002、BE-005。

验收标准：

- 邀请码唯一。
- 一个关系最多两个有效成员。
- 一个用户同一时间只能处于一个有效关系。

### BE-011 关系接口

内容：

- 实现 `POST /relationships`。
- 实现 `POST /relationships/join`。
- 实现 `GET /relationships/current`。
- 实现 `POST /relationships/current/break`。
- 实现关系天数计算。

依赖：BE-008、BE-010。

验收标准：

- 用户可创建关系并获得邀请码。
- 第二个用户可加入关系。
- 第三个用户加入同一关系返回 `RELATIONSHIP_FULL`。
- 已有关系用户加入新关系返回 `ALREADY_IN_RELATIONSHIP`。
- 解除关系后不可继续写入业务数据。

### BE-012 关系权限守卫

内容：

- 实现当前关系解析服务。
- 实现关系成员权限校验。
- 为打卡、目标、消息、日历模块复用。

依赖：BE-011。

验收标准：

- 用户不能访问非本人关系数据。
- 无当前关系时返回明确业务错误。
- 关系已解除时写接口返回 `RELATIONSHIP_INACTIVE`。

### BE-013 打卡模型

内容：

- 建立 `daily_checkins` 表。
- 添加唯一约束 `(relationship_id, user_id, checkin_date)`。
- 定义 mood 枚举。

依赖：BE-010。

验收标准：

- 同一用户同一天不能产生多条有效打卡。
- note 长度限制生效。

### BE-014 今日打卡接口

内容：

- 实现 `POST /checkins/today`。
- 实现 `GET /checkins/today`。
- 按用户或关系时区确定今日日期。
- 支持当天覆盖更新或返回冲突，按产品策略实现。

依赖：BE-012、BE-013。

验收标准：

- 可提交 happy/normal/sad。
- 可返回自己和对方今日完成状态。
- 不能提交未来日期。
- 无关系用户不可打卡。

### BE-015 连续打卡计算

内容：

- 实现双方共同连续完成天数计算。
- 返回今天双方状态。
- 编写单元测试覆盖边界。

依赖：BE-014。

验收标准：

- 双方连续完成 N 天时返回 N。
- 今天只有一方完成时按规则返回昨天为止连续天数。
- 中断日期后计算停止。

### BE-016 打卡时间线

内容：

- 实现 `GET /checkins/timeline`。
- 支持 cursor 或 page 分页。
- 支持日期范围过滤。
- 返回用户资料和打卡内容。

依赖：BE-014。

验收标准：

- 列表按时间倒序。
- 默认 limit 合理，例如 20。
- 只能返回当前关系数据。

### BE-017 首页聚合接口

内容：

- 实现 `GET /dashboard`。
- 聚合关系、成员、连续打卡、对方今日状态、当前目标摘要。
- 处理无关系、pending 关系、active 关系。

依赖：BE-011、BE-015、BE-021。

验收标准：

- 前端首页所需数据一次返回。
- 无目标时 `goal` 可为 null。
- 对方未打卡时 partnerToday 返回空状态。
- P95 目标小于 500ms。

### BE-018 目标模型

内容：

- 建立 `goals` 表。
- 建立 `goal_entries` 表。
- 定义目标状态枚举。
- 添加金额字段整数存储。

依赖：BE-010。

验收标准：

- 目标和流水表迁移成功。
- 目标金额不可小于等于 0。
- 流水金额约束明确。

### BE-019 目标接口

内容：

- 实现 `GET /goals/current`。
- 实现 `POST /goals`。
- 实现 `PATCH /goals/:goalId`。
- 实现 `GET /goals/:goalId/entries`。

依赖：BE-012、BE-018。

验收标准：

- 每个关系可获取当前 active 目标。
- 无 active 目标返回空状态。
- 非当前关系目标不可访问。

### BE-020 目标金额流水

内容：

- 实现 `POST /goals/:goalId/entries`。
- 使用事务写入流水并更新 `current_amount`。
- 判断目标是否达成。
- 达成后写入 `completed_at`。

依赖：BE-019。

验收标准：

- 金额更新和流水写入原子完成。
- 并发提交不会造成金额错乱。
- 达成目标后状态为 `completed`。
- 目标已完成后继续写入策略明确。

### BE-021 当前目标摘要服务

内容：

- 为 dashboard 提供当前目标摘要。
- 计算 progress。
- 处理无目标和已完成目标。

依赖：BE-019、BE-020。

验收标准：

- 首页可展示目标标题、金额、进度。
- progress 保持 0 到 1 或按约定允许超过 1。

### BE-022 日历聚合接口

内容：

- 实现 `GET /calendar?month=YYYY-MM`。
- 查询当前关系某月双方打卡记录。
- 聚合每天状态：both、me_only、partner_only、none、future。
- 返回双方 mood 摘要。

依赖：BE-012、BE-014。

验收标准：

- 月份参数非法返回校验错误。
- 未来日期标记为 future。
- 只能返回当前关系数据。
- 跨月边界日期处理正确。

### BE-023 消息模型

内容：

- 建立 `messages` 表。
- 定义消息类型：daily_word、reply、system。
- 添加软删除字段。

依赖：BE-010。

验收标准：

- 消息内容长度限制生效。
- 删除不物理移除数据。

### BE-024 消息接口

内容：

- 实现 `GET /messages`。
- 实现 `POST /messages`。
- 实现 `DELETE /messages/:messageId`。
- 支持日期过滤和分页。

依赖：BE-012、BE-023。

验收标准：

- 用户可发送消息。
- 用户只能删除自己发送的消息。
- 列表不返回软删除消息。
- 消息只在当前关系范围内可见。

### BE-025 设置接口

内容：

- 实现 `GET /settings`。
- 实现 `PATCH /settings`。
- 支持通知开关、每日提醒时间、隐私级别。

依赖：BE-005、BE-008。

验收标准：

- 用户只能修改自己的设置。

### BE-026 数据导出骨架

验收标准：

- 接口结构稳定，前端可接入。

### BE-027 通知预留

- 数据库迁移和 seed 步骤明确。

## 6. 数据库迁移顺序

建议迁移顺序：

1. `users`
2. `user_settings`
3. `auth_codes` 或 Redis 结构说明
4. `relationships`
5. `relationship_members`
6. `daily_checkins`
7. `goals`
8. `goal_entries`
9. `messages`
10. `notification_tokens`
11. `exports`

关键约束：

- `users.email` 唯一。
- `relationships.invite_code` 唯一。
- `daily_checkins(relationship_id, user_id, checkin_date)` 唯一。
- `relationship_members` 需要保证一个关系最多两个有效成员。
- 用户当前有效关系唯一约束需要结合业务逻辑或部分索引实现。

## 7. 前后端联调计划

### 联调准备

后端需要提供：

- Swagger/OpenAPI 地址。
- 本地 API base URL。
- 测试账号或开发环境验证码获取方式。
- 种子数据说明。
- 错误码说明。

### 联调顺序

1. 认证接口：验证码、登录、刷新 token。
2. 当前用户接口：`/me`。
3. 关系接口：创建、加入、当前关系。
4. 首页接口：`/dashboard`。
5. 打卡接口：提交今日打卡、查询今日状态。
6. 目标接口：当前目标、添加流水。
7. 日历接口：月数据。
8. 消息接口：列表和发送。
9. 设置接口：读取和更新。
10. 解除关系和异常状态。

### 联调验收

- 前端不需要为同一页面拼接过多接口，首页应尽量依赖 `/dashboard`。
- 后端错误码和前端提示能对应。
- 关键字段命名保持一致。
- 日期和时区规则前后端一致。

## 8. 后端验收清单

MVP 完成时需要确认：

- 服务可启动，健康检查可用。
- 数据库迁移可执行。
- Swagger 文档完整。
- 邮箱验证码登录可用。
- token 刷新和退出可用。
- 用户可创建关系和邀请码。
- 第二个用户可加入关系。
- 成员权限校验覆盖所有关系资源。
- 用户可提交今日打卡。
- 首页可返回前端需要的聚合数据。
- 连续打卡天数计算准确。
- 用户可创建目标和添加金额流水。
- 目标达成逻辑准确。
- 日历接口可返回某月状态。
- 消息发送、查询、删除可用。
- 设置接口可用。
- 关键单元测试和集成测试通过。

## 9. 风险与处理建议

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 时区定义不清 | 打卡日期和连续天数错误 | 首期统一使用用户时区或关系创建者时区，并在接口返回 date |
| 关系唯一约束复杂 | 用户可能加入多个关系 | 数据库约束加业务事务双重保护 |
| 首页聚合变慢 | 首页体验差 | 先优化查询和索引，再考虑缓存 |
| 目标金额并发写入 | 金额错乱 | 金额流水和目标更新必须事务处理 |
| 验证码被滥用 | 邮件成本和安全风险 | 邮箱、IP、设备多维限流 |
| 前后端字段不一致 | 联调返工 | 早期生成 OpenAPI 并冻结 MVP 字段 |

## 10. 推荐开发顺序

最小可用路径：

1. BE-001 至 BE-004：工程和接口基础。
2. BE-005 至 BE-008：认证闭环。
3. BE-010 至 BE-012：关系和权限。
4. BE-013 至 BE-017：打卡和首页。
5. BE-018 至 BE-022：目标和日历。
6. BE-023 至 BE-025：消息和设置。
7. BE-026 至 BE-032：导出骨架、通知预留、测试、部署。

优先级最高的是认证、关系、打卡和首页聚合，因为前端 MVP 的核心页面都依赖这些能力。

## 11. 首期可暂缓实现项

为了控制 MVP 范围，以下能力可暂缓：

- 真实邮件服务正式接入，开发阶段可 mock。
- 复杂通知推送。
- 数据导出完整文件生成。
- 管理后台。
- 图片、语音、视频消息。
- 多目标并行管理。
- 历史关系恢复和切换。
- 内容审核系统。
